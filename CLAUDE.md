# CLAUDE.md — eclipse-site

This repo is the `eclipse.deyderae.dev` subdomain. Before making changes, read **`DESIGN.md`** from the `deyderae-site` repo — it's the design document for the whole `deyderae.dev` domain (architecture, security, and workflow standards apply here too, even though the canonical copy lives in that repo). On the author's machine it's at `../deyderae-site/deyderae-site/DESIGN.md` (relative to this repo's root; note the extra wrapper folder). If it isn't there, don't guess at its contents or proceed from memory: stop and ask the user to provide it.

## What this repo is
Eclipse: live character-sheet hosting and a read-only DM roster for one tabletop campaign (Age of Eclipse), backed by Supabase. Deployed to Cloudflare Workers (static assets) via Wrangler, same as `deyderae-site`, but as its own independent Worker/repo (see DESIGN.md §3.1 — subdomains don't share a deploy or a runtime).

It is being built in phases from `docs/IMPLEMENTATION_PLAN.md`. Accounts (sign-up, password and magic-link sign-in, password reset, the account page), the campaign home page, joining by invite, and the DM's invite management (create, list, revoke) are built (ADR 0007, steps 0 and 1; the dashboard for several campaigns, CAPTCHA and two-factor are steps 2 and 3). The player sheet at `/campaign/:id/play` is built (ADR 0008): the V4 sheet ported into the app, saving to Supabase. The DM roster is built too (ADR 0009): player cards, a live read-only view of each sheet, and a "download all sheets" backup. `legacy/` holds the two single-file sheets (V4 and V5) the sheet was ported from, and V4's own colour theme (`v4-theme.css`); it is reference material and is not published.

## Architecture (decided; see `docs/adr/`)
- A plain HTML/CSS/JS single-page app: no framework and no bundler (DESIGN.md §3.2). Real URLs via a small History-API router; `wrangler.jsonc` sets `not_found_handling` to `single-page-application` so deep links get `index.html`.
- **Supabase** (Postgres + Auth + Realtime) is the backend, a deliberate exception to the domain's Cloudflare D1 default (DESIGN.md §3.3.1). Two layers guard every table: explicit GRANTs (ADR 0003) and Row Level Security. A player reads and writes their own sheet (only while a member); the DM can read every sheet in their campaign and can never write one (ADR 0001, 0002).
- **Accounts are Supabase Auth** (ADR 0007): email and password, or a magic link, both with the PKCE flow. Supabase stores each password as a salted bcrypt hash; the app only sends it to Supabase over TLS and must never store, hash, log or echo one. Minimum 12 characters, maximum 72 bytes, no composition rules (`validatePassword` in `js/util.js`; the server enforces the same minimum). Emailed links must be opened in the browser that asked for them. Errors shown to people go through `friendlyError` and never say whether an email exists. `?next=` return paths go through `safeNextPath` (same-site paths only). A trigger on `auth.users` creates the profile row (migration 0007). Don't hand-roll sessions.
- **Who can create a campaign:** only people on the `campaign_creators` allowlist (ADR 0005). Nobody can add themselves; the owner manages it with `npm run creators add|remove|list <email>` (plain words, no `--`, which PowerShell drops) (the person must have signed in once). Campaign creation is closed by default.
- **How players join:** only through an invite the DM creates on the DM page. Invites are server-generated (120 bits), stored only as a SHA-256 hash, expiring, use-limited, revocable, and shown to the DM once. The client never generates or stores a code, and the API never returns one (`create_invite` / `revoke_invite` / `join_campaign`, ADR 0005). Sign-up can stay open because an account with no invite and no allowlist entry can do and see nothing.
- **Nothing is ever deleted by a client.** The DELETE grants and policies on campaigns and characters are gone, and a trigger snapshots every delete, every `schema_version` change and (at most every 10 minutes) every edit into `character_history` (ADR 0004).
- Eclipse hosts one campaign of about a dozen players, and the sheet and rules will change over time (ADR 0004).

## Working in this repo now
- **Only `public/` is published.** `wrangler.jsonc` sets `assets.directory` to `./public`; everything in that folder is served publicly, and nothing outside it is. Site files (HTML/CSS/JS/images/fonts, plus `_headers` / `_redirects`) go in `public/`. Repo tooling and docs (`wrangler.jsonc`, `package.json`, `CLAUDE.md`, `supabase/`, `legacy/`, `docs/`, `scripts/`) stay at the repo root. Wrangler does not skip `.git` or `node_modules` when uploading, so pointing `assets.directory` back at the repo root would publish them (and fail the deploy on large binaries).
- **Verifying what is published.** `npx wrangler deploy --dry-run` must exit 0 and report `Read N files`, where N counts every file **and subdirectory** under `public/` (`find public -mindepth 1 | wc -l`, currently 54). Because of the SPA fallback, a request for a path that does not exist answers `200` with the app shell, not `404`. So the check for `/DESIGN.md`, `/wrangler.jsonc`, `/package.json`, `/.git/config` and the like is that the response is the app shell (`<title>Eclipse</title>`) and never the file's contents. Do not run a real deploy to verify.
- Layout of `public/`: `index.html` (shell), `style.css` (site), `sheet.css` (the sheet only, all scoped to `.sheet`), `script.js` (theme switcher only), `logo.svg`, `_headers` (security headers and CSP), `js/` (the app's ES modules), `vendor/` and `fonts/` (third-party files, never edited).
- **The sheet's code** (ADR 0008). `js/eclipse-rules.js` holds the state shape and every rule as pure functions (no DOM, no Supabase; the DM roster will import it too). `js/characters.js` reads and writes the player's row, `js/autosave.js` is the debounce and retry state machine. `js/roster.js` (pure) builds the DM's roster and backup file from rows, `js/roster-view.js` draws it, and `js/data.js` has the DM's reads and the Realtime subscription. `js/sheet/` is the view: `*-page.js` build each page with `h()`, `render.js` draws numbers from the inputs, `bindings.js` turns input into changes to the sheet, `rebuild.js` redraws rows that come and go, `files.js` reads and writes `.eclipse` files, `index.js` is the view (tabs, save bar, conflicts).
- **Sheet rules that must hold.** Store inputs only, never a computed number. A sheet is only shown after it loaded and `openSheet` read it; never write before that. Unknown fields are kept (`normalize`). A stored `schema_version` newer than `SCHEMA_VERSION` opens read-only. A rename, removal or retype of a stored field is a new `SCHEMA_VERSION` plus a step in `MIGRATIONS`, never silent. Saves are conditional on `updated_at`; a mismatch is a conflict the player resolves, never an overwrite. A stored name that picks a row from a rules table goes through `own()` (so "constructor" matches nothing).
- **The DM's pages only read.** No insert, update, delete or RPC from the roster or the DM's sheet view (`sheet/index.js` with `viewer: "dm"` is read only). Realtime only tells the page to look; `syncRoster` re-reads changed rows by `updated_at`, and a 30 second check backs it up. `tests/e2e/fake-supabase.js` fakes the Realtime websocket (`window.__realtime.emit()` and `.drop()`).
- **Fonts are self-hosted**: `npm run vendor` copies the pinned `@fontsource` Latin woff2 files and their OFL licenses into `public/fonts/`; `font-src 'self'` is in `_headers`. Asset URLs are root-absolute (`/style.css`, `/js/app.js`) because deep links like `/campaign/x/play` would break relative ones.
- **The Supabase client is vendored.** `public/vendor/supabase.js` is a byte-for-byte copy of the pinned `@supabase/supabase-js` browser bundle (the CSP allows scripts from `'self'` only, and there is no build step). Never edit it. To upgrade: change the version in `package.json`, `npm install`, `npm run vendor`, commit the result.
- `public/js/config.js` holds the project URL and anon key. Both are public by design (RLS and grants protect the data). Never put the service_role/secret key or the database password anywhere under `public/`.
- **Rendering rule:** build DOM with `js/dom.js` (`h()`, and `s()` for SVG), which only ever adds text as text nodes. Never use `innerHTML`, `insertAdjacentHTML` or `document.write` with anything that came from the database or the user: campaign, player and character names are user-controlled. The one exception is `staticHtml()`, for markup that lives in this repo (the Reference cards); `tests/unit/sources.test.js` fails on any other use. Attach handlers with `addEventListener` (the `on*` props of `h()` do this), never as inline attributes. No `style` attributes either: use a class, or set a CSS custom property from script (`el.style.setProperty("--pos", ...)`, which the CSP allows).
- Keep `js/util.js` and the matcher in `js/router.js` free of DOM and Supabase imports so they stay unit-testable in Node.
- Accessibility of navigation: after an in-app navigation focus moves to the new `<h1>`; on the first render it does not (moving it there would make Tab skip the skip link and the header).
- The theme system (Catppuccin, 4 palettes, `data-theme` attribute + `localStorage`) is duplicated from `deyderae-site`. Per DESIGN.md §3.4 that duplication is a known issue to fix, not a pattern to copy again — check whether a shared source has been extracted before touching it. In `public/style.css`, everything above the `Site layout` comment (palettes, reset, `color-scheme`) is the shared block and must stay byte-identical to the first 62 lines of `deyderae-site`'s `public/style.css`; don't change it here without changing the apex too. Eclipse-only CSS goes below that comment, and the theme logic in `public/script.js` stays separate from any site-specific code. `public/logo.svg` is a shared asset copied from the apex, so the same rule applies to it.
- No inline `<script>`, `<style>`, `style=` attributes, `on*` handlers, or `data:` URIs (DESIGN.md §4, §5.1) — they block the strict CSP in `public/_headers`. That policy allows scripts, styles and images from `'self'` only, and `connect-src` only for this project's Supabase origin (`https://` and `wss://`). Any new origin (a font host, another API) must be added there deliberately; never use `unsafe-inline` or `unsafe-eval`. The legacy sheets are **not** CSP-clean (inline `<style>`/`<script>` blocks and about 90 `style="..."` attributes each), so porting them means moving that into `style.css` and `js/`. Self-host fonts (woff2 in `public/fonts/`, `font-src 'self'`); don't load Google Fonts.
- New colours must meet WCAG AA in all four themes, Latte especially (DESIGN.md §4). The sheet has two kinds of accent token in `sheet.css` (plain for fills and borders at 3:1, `-t` for text at 4.5:1), and `tests/unit/contrast.test.js` checks both in every theme, so add a colour there and run `npm test`: use `--text`/`--subtext1` for small text, never `--subtext0` or `--overlay*`, and for coloured links or badges mix the accent toward `--text` (`--link` is `color-mix(in srgb, var(--blue) 75%, var(--text))`). Form and button borders need 3:1 against their background (`--field-border` is 70% `--text` into `--base`; 62% failed on Latte). Large text (24px, or 18.66px bold) only needs 3:1. Don't dim disabled things with `opacity`; use a dashed border. Never write `*/` inside a CSS comment — it closes the comment early and silently swallows the next rule.
- `package.json` pins dev tooling and nothing runs from `node_modules` in production: Wrangler (`npm run dev` for local preview on port 8787, `npm run deploy` for production, until CI/CD from DESIGN.md §6.3 exists), the Supabase CLI (also behind `npm run creators`), and `@supabase/supabase-js` (only as the source for `npm run vendor`). All are pinned exactly where DESIGN.md §5.4 asks. `npx supabase ...` resolves the local CLI; don't install it globally.
- **Database changes** are new numbered files in `supabase/migrations/`, never edits to an applied one, applied with `npx supabase db push` (run `--dry-run` first). A new table needs its RLS policy **and** its GRANTs in the same migration (ADR 0003), and `supabase/tests/grants.test.sql` extended. Grants are **per column** for INSERT and UPDATE (ADR 0006): a column the server controls (ids, timestamps, foreign keys) must never be client-writable, so a new writable column needs an explicit grant and an assertion. The test harness (`supabase/tests/local_auth_harness.sql`) must mirror the real platform's default privileges and never be more permissive. Run `npm run test:db` (harness, every migration, every `*.test.sql` suite, in a throwaway database; needs a Postgres, use 17 to match the live project) for any change that touches the schema. Every suite raises on failure, so it can gate CI. A code from `create_invite` is unrecoverable by design: if a link is lost, revoke that invite and create a new one.
- **Supabase project settings** are mirrored in `supabase/config.toml`, which is deliberately minimal. `npx supabase config push` writes everything declared there to the LIVE project, and the CLI fills undeclared sections with its own defaults, so never regenerate this file from `supabase init`, and always run `npx supabase config diff` before a push.
- Tests: `npm test` runs the unit tests (Vitest, `tests/unit/`, including the rules, autosave, contrast and source checks); `npm run test:db` runs the database suites. `npm run test:e2e` runs the browser suite (Playwright, `tests/e2e/`) against the real `wrangler dev` server, so the real CSP applies; it uses Edge (`E2E_CHANNEL=chromium` elsewhere). `tests/e2e/fake-supabase.js` stands in for Supabase inside the page (including a `characters` table that enforces the column grants and the `updated_at` match), and every test fails on a CSP violation or an uncaught error. It cannot prove that email arrives. There is no CI yet (DESIGN.md §6.3).
- Once this app handles user data, treat DESIGN.md §5.5 (input validation, rate limiting, least-privilege bindings) as required reading before writing any backend logic, not optional hardening to add later. Every new table is a security decision.

## Don't
- Don't lose a character. Eclipse hosts one campaign of about a dozen players, and the sheet and rules will keep changing (docs/adr/0004-scale-and-data-preservation.md): never build UI that deletes a campaign or character, never write a sheet before it has loaded successfully, keep unknown fields on save, and make non-additive sheet changes versioned (`characters.schema_version` plus a `migrate()` step), not silent.
- Don't point `assets.directory` in `wrangler.jsonc` back at the repo root, and don't put non-site files (docs, config, source that isn't served, secrets) in `public/`.
- Don't commit secrets, tokens, or (once there's a database) real user data/fixtures.
- Don't put the Supabase service role key in client code, the repo, or logs — it bypasses RLS entirely. The `anon` key is public by design; RLS is what makes that safe (DESIGN.md §5.3).
- Don't wire this Worker directly to a shared database credential used by other subdomains — route through a dedicated API service if cross-subdomain data sharing is ever needed (DESIGN.md §3.3). Eclipse's Supabase project is its own boundary: nothing else on the domain should hold its service role key or read its tables directly (DESIGN.md §5.6).
