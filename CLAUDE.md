# CLAUDE.md — eclipse-site

This repo is the `eclipse.deyderae.dev` subdomain. Before making changes, read **`DESIGN.md`** from the `deyderae-site` repo: it is the design document for the whole `deyderae.dev` domain (architecture, security and workflow standards apply here too). On the author's machine it is at `../deyderae-site/deyderae-site/DESIGN.md` (note the extra wrapper folder). If it is not there, do not guess at its contents: stop and ask the user for it.

This file holds the rules. How the system works today (roles, tables, who can do what, database functions, pages, limits) is in **`docs/system.md`**; read it first. Steps for running, testing, backing up and releasing are in **`README.md`**. Why each choice was made is in **`docs/adr/`** (history: where an ADR and `docs/system.md` disagree, the code and `docs/system.md` win). When a change makes `docs/system.md` or this file wrong, fix them in the same change.

## What this repo is
Eclipse: live character sheets and a read-only Keeper roster for the campaigns of one tabletop game (Age of Eclipse). A plain HTML/CSS/JS single-page app with no framework and no bundler (DESIGN.md §3.2), served as static assets by its own Cloudflare Worker (DESIGN.md §3.1), with Supabase (Postgres, Auth, Realtime) behind it, a deliberate exception to the domain's D1 default (DESIGN.md §3.3.1). About 10 people, at most 4 campaigns (ADR 0014); the sheet and rules keep changing (ADR 0004). Still to build: the dashboard for several campaigns, CAPTCHA, breached-password screening and two-factor (ADR 0007 steps 2 and 3), and the sheet's "Campaign" entry (GitHub issues).

## Where the code is
- `public/` is the whole published site. `index.html` (shell), `style.css` (site), `sheet.css` (the sheet only, scoped to `.sheet`), `script.js` (theme switcher only), `logo.svg`, `_headers` (security headers and CSP), `js/` (the app's ES modules), `vendor/` and `fonts/` (third-party, never edited).
- `js/app.js` is the router table (`ROUTES`) and startup only. Each area's pages are in `account-routes.js`, `character-routes.js`, `campaign-routes.js` (home, joining, the Keeper's pages) and `rulebook-routes.js`. `shell.js` has `show()` and the leave gate `mayLeave()`; `sheet-page.js` has `showReadOnlySheet()`; `confirm-dialog.js` has `confirmAction()`, the one "are you sure?" dialog (never `window.confirm`). `views.js`, `character-views.js`, `history-view.js`, `roster-view.js`, `invite-panel.js`, `rulebook-view.js` draw pages; `characters.js`, `data.js`, `rulebook.js`, `admin.js`, `auth.js` talk to Supabase.
- The sheet (ADR 0008): `eclipse-content.js` holds the game's content (every table, name and rule number, once; each table marked `Stored` or `Not stored`). `eclipse-rules.js` holds the state shape and every rule as pure functions. `sheet/fields.js` is the one list of the sheet's inputs (ADR 0019): each has a path, kind and label, and its input carries `data-f="<path>"`; `sheet/bindings.js` writes and `sheet/render.js` fills every input from that list, so a new field is one entry there. `sheet/*-page.js` build the six pages, numbered 1 to 6 in the order shown (Core, Equipment, Casting, Testament, Log, Reference). A Reference table that repeats a rule is data in `sheet/reference-data.js`, checked by `tests/unit/content.test.js`; a card's `book` is a rulebook chapter slug.
- Pure modules with no DOM or Supabase import, so Node tests them: `util.js`, `eclipse-content.js`, `eclipse-rules.js`, `roster.js`, `character-list.js`, `history.js`, and the matcher and leave gate in `router.js`. Keep them that way; `parseMarkdown` in `markdown.js` stays pure too.
- Outside `public/`: `supabase/` (migrations, the two config files, SQL test suites), `scripts/` (the owner's npm scripts), `tests/unit/`, `tests/e2e/`, `docs/`.

## Rules

### Words
- **The game master is the Keeper.** Use "Keeper" in every text a person sees and in the docs, never "DM" or "GM". Code and database names that already say `dm` keep it: a rename costs a migration and helps nobody.

### Publishing
- **Only `public/` is published** (`assets.directory` in `wrangler.jsonc`). Never point it back at the repo root (Wrangler would upload `.git` and `node_modules`), and never put docs, config, unserved source or secrets in `public/`.
- `npx wrangler deploy --dry-run` must exit 0 and report `Read N files`, where N counts every file and subdirectory under `public/` (`find public -mindepth 1 | wc -l`, currently 72; CI checks it). Because of the SPA fallback, a missing path answers `200` with the app shell, so the check for `/DESIGN.md`, `/package.json`, `/.git/config` and the like is that the answer is the shell (`<title>Eclipse</title>`), never the file. Do not run a real deploy to verify.
- Cloudflare Workers Builds deploys every merge into `main`. So a migration goes to staging and live before its pull request is merged (README, Releasing a change).

### Security
- **Every table is a security decision.** Read DESIGN.md §5.5 before any backend logic. Two layers guard every table: explicit GRANTs (ADR 0003) and Row Level Security. A new table gets its RLS policy **and** its GRANTs in the same migration, and `supabase/tests/grants.test.sql` is extended. INSERT and UPDATE grants are **per column** (ADR 0006): a column the server controls (ids, timestamps, foreign keys, `deleted_at`) is never client-writable. The test harness (`supabase/tests/local_auth_harness.sql`) mirrors the platform's default privileges and is never more permissive; its `supabase_auth_admin` has nothing in `public` that a migration does not grant.
- **Never** put the service role key or the database password in `public/`, the repo or logs. `public/js/config.js` holds the project URL and anon key, public by design. Nothing else on the domain holds Eclipse's service role key or reads its tables (DESIGN.md §3.3, §5.6).
- **Accounts are Supabase Auth** with PKCE (ADR 0007). Don't hand-roll sessions. The app sends a password only to Supabase and never stores, hashes, logs or echoes one; `validatePassword` (`util.js`) matches the server: 12 characters minimum, 72 bytes maximum, no composition rules. Every error a person sees goes through `friendlyError` and never says whether an email exists; `tests/unit/errors.test.js` checks that every `raise exception` in the migrations has a message there, so a new or reworded raise needs a matching line. `?next=` goes through `safeNextPath`.
- **Sign-up is closed to unapproved emails** by the Auth hook `hook_require_approved_email` (ADR 0014), set in both config files; `enable_signup` stays `true`. A refused sign-up shows the same text as any other (`isUnapprovedEmail`). Only the owner manages site admins and campaign creators (`npm run admins`, `npm run creators`); nobody can add themselves.
- **Invites** are made, stored (a SHA-256 hash only) and checked by the server (ADR 0005, 0012). The client never makes or stores a code, and the API returns one only once, to the Keeper who made it.
- **Rendering:** build DOM with `h()` and `s()` from `js/dom.js`, which add text only as text nodes. Never use `innerHTML`, `insertAdjacentHTML` or `document.write`. The one exception is `staticHtml()`, for markup that lives in this repo (the Reference cards); `tests/unit/sources.test.js` fails on any other use. The Markdown reader (`markdown.js`) makes only its own tags and attributes; `tests/unit/markdown.test.js` checks that no other can appear.
- **CSP** (`public/_headers`): scripts, styles, images and fonts from `'self'` only; `connect-src` only the live Supabase origin. No inline `<script>` or `<style>`, no `style=` attributes, no `on*` attributes, no `data:` URIs (DESIGN.md §4, §5.1): attach handlers with `addEventListener` (the `on*` props of `h()` do), and style with a class or a CSS custom property set from script. Never add `unsafe-inline` or `unsafe-eval`; add a new origin only on purpose. Nothing in `public/` names the staging project (`tests/unit/projects.test.js`).
- Fonts are self-hosted (`npm run vendor`); never load Google Fonts. `public/vendor/supabase.js` is a byte-for-byte copy of the pinned bundle: never edit it; to upgrade, change `package.json`, `npm install`, `npm run vendor`, commit.
- **No text of the real rulebook is ever in this repo** (code, tests, fixtures, docs, commit messages), because the repo is public (ADR 0016). Tests use made-up chapters. A Reference card may name a chapter by its slug only. The book lives in a private repo and reaches the site only through `npm run rulebook push`.

### Never lose a character
- Nothing is ever deleted by a client, with one exception (ADR 0004, 0018). Never build UI that deletes a campaign or removes a character: `delete_character` only hides one, and `purge_character` (the owner, their own already-archived character) is the one real delete.
- The Keeper's pages never write a sheet: no insert, update, delete or RPC from them. Their two actions (`remove_player`, the invite form) are callbacks the Keeper page gives them. A sheet view is read only when given a `readOnlyNotice`. A Keeper page opens a character only while it is active in that campaign. Realtime only tells a page to look: it re-reads rows, never trusts the message.
- Restoring goes through `restore_character_version()`, never a plain update.
- **Sheet rules.** Store inputs only, never a computed number. Show a sheet only after it loaded and `openSheet` read it; never write before that. Keep unknown fields (`normalize`). A stored `schema_version` newer than `SCHEMA_VERSION` opens read only. Saves are conditional on `updated_at`; a mismatch is a conflict the player resolves, never an overwrite. A stored name that picks a row from a rules table goes through `own()`. For a rules change follow ADR 0013: adding a field or a table row needs nothing more; a rename, removal or retype of a stored field, or a change to a number marked Stored (`MONITOR_BOXES`, `TRACK_MAX`), needs a new `SCHEMA_VERSION` and a tested step in `MIGRATIONS`; a row of a Stored table is retired, never deleted, once a sheet can point at it. Run `npm run rehearse <backup>` before shipping a migration step.

### Views
- Change the view only through the router, never by calling `onRoute`. A view that may hold unsaved changes gives `show()` a `flush`; before every change of view the router asks `mayLeave()`, which asks the person (with `confirmAction`) only when `flush` resolves false. Once a view is left, `main` is `inert` until the next `show()`.
- After an in-app navigation, focus moves to the new `<h1>`; on the first render it does not.

### Look
- Header, footer and page layout follow deyderae.dev: the header is the apex site's (full width, brand at the left edge, account buttons and theme switcher at the right, sticky from 40rem), and its CSS is copied from the apex (DESIGN.md §3.4). `.page` is 72rem; content is a 50rem column unless `show()` is given `roomy` or `wide`. The rulebook alone is given `full`: up to 120rem, paragraphs capped at 80 characters.
- The theme system is duplicated from `deyderae-site` (DESIGN.md §3.4 calls this a known issue; check for a shared source before touching it). Everything above the `Site layout` comment in `public/style.css` stays byte-identical to the first 62 lines of the apex's `public/style.css`, and `public/logo.svg` stays identical to the apex's; change them there too or not at all.
- New colours meet WCAG AA in all four themes, Latte especially (DESIGN.md §4), and go into `tests/unit/contrast.test.js`. Small text uses `--text`/`--subtext1`, never `--subtext0` or `--overlay*`; in `sheet.css` a plain accent token is for fills and borders (3:1), a `-t` token for text (4.5:1); a coloured link mixes its accent toward `--text` (like `--link`). Form and button borders need 3:1. Show "disabled" with a dashed border, never `opacity`. Never write `*/` inside a CSS comment.

### Database and projects
- A database change is a new numbered file in `supabase/migrations/`, never an edit to an applied one. Run `npm run test:db` (Postgres 17) for any schema change; every suite raises on failure. Push with `npx supabase db push --dry-run`, then `npx supabase db push` (live) and `npm run staging push` (staging).
- `supabase/config.toml` (live) and `supabase/staging.config.toml` are deliberately minimal. `npx supabase config push` writes every declared section to LIVE and fills the rest with CLI defaults: never regenerate either file from `supabase init`, and run `npx supabase config diff` (or `npm run staging check`) before a push. `tests/unit/config.test.js` keeps the two in step.
- **Development uses the staging project** (ADR 0015), never live: `npm run dev` serves a copy of `public/` that names staging. Never link the repo to staging. The owner's scripts take plain words only (`npm run rulebook push <folder> staging`, never `--staging`: npm swallows it and the script would use live).
- Tooling is pinned in `package.json` (DESIGN.md §5.4) and nothing from `node_modules` runs in production. Use `npx supabase ...`; don't install the CLI globally.

### Tests
- `npm test` (Vitest, `tests/unit/`), `npm run test:db` (the SQL suites), `npm run test:e2e` (Playwright and an axe scan of every page in two themes, against the real `wrangler dev` server and CSP; Edge by default, `E2E_CHANNEL=chromium` elsewhere; `E2E_PORT` changes the port so two runs can share a machine). `tests/e2e/fake-supabase.js` stands in for Supabase and enforces the column grants, the `updated_at` match, the character limit, the sign-up hook and the admin checks; keep it at least as strict as the real project. Every browser test fails on a CSP violation or an uncaught error.
- CI runs `unit`, `database`, `browser`, `publish`, `vendor` and `audit` on every push and pull request, and `main` needs all of them green. Dependabot's `vendored` group fails `vendor` until someone runs `npm run vendor` on its branch and commits the result.

## Don't
- Don't lose a character (above).
- Don't point `assets.directory` at the repo root, or put non-site files in `public/`.
- Don't commit secrets, tokens, real user data, or text from the real rulebook.
- Don't put the service role key in client code, the repo or logs: it bypasses RLS entirely (DESIGN.md §5.3).
- Don't wire this Worker to a database credential another subdomain uses; share data through a dedicated API if ever needed (DESIGN.md §3.3).
