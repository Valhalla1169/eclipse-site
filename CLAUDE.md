# CLAUDE.md — eclipse-site

This repo is the `eclipse.deyderae.dev` subdomain. Before making changes, read **`DESIGN.md`** from the `deyderae-site` repo — it's the design document for the whole `deyderae.dev` domain (architecture, security, and workflow standards apply here too, even though the canonical copy lives in that repo). On the author's machine it's at `../deyderae-site/deyderae-site/DESIGN.md` (relative to this repo's root; note the extra wrapper folder). If it isn't there, don't guess at its contents or proceed from memory: stop and ask the user to provide it.

## What this repo is
Eclipse: live character-sheet hosting and a read-only Keeper roster for the campaigns of one tabletop game (Age of Eclipse), backed by Supabase. Deployed to Cloudflare Workers (static assets) via Wrangler, same as `deyderae-site`, but as its own independent Worker/repo (see DESIGN.md §3.1 — subdomains don't share a deploy or a runtime).

What is built: accounts (sign-up for an email a site admin approved, password and magic-link sign-in, password reset, the account page, and the Admin page at `/admin` where a site admin approves emails, ADR 0014), the campaign home page, joining by invite, and the Keeper's invite management (create, list, revoke) are built (ADR 0007, steps 0 and 1; the dashboard for several campaigns, CAPTCHA and two-factor are steps 2 and 3). The player sheet is built (ADR 0008): the V4 sheet ported into the app, saving to Supabase, at `/characters/:id`. Characters belong to people, not campaigns (ADR 0011): up to 5 each (ADR 0014), and one active per campaign, chosen at `/campaign/:id/character`. The Keeper roster is built too (ADR 0009): player cards, a live read-only view of each sheet, and a "download all sheets" backup. A player can look at earlier copies of their sheet and put one back, and a Keeper can look at the copies kept since a character became active in their campaign (ADR 0010, 0011). Still to build: the dashboard for several campaigns, CAPTCHA, breached-password screening and two-factor (ADR 0007 steps 2 and 3). A player can leave a campaign, and a Keeper can remove one, from buttons (ADR 0012); coming back needs a new invite. The player's rulebook is readable by signed-in people at `/rules` (ADR 0016). A "Campaign" entry at the top of the sheet is planned (the repo's GitHub issues).

## Architecture (decided; see `docs/adr/`)
- A plain HTML/CSS/JS single-page app: no framework and no bundler (DESIGN.md §3.2). Real URLs via a small History-API router; `wrangler.jsonc` sets `not_found_handling` to `single-page-application` so deep links get `index.html`.
- **Supabase** (Postgres + Auth + Realtime) is the backend, a deliberate exception to the domain's Cloudflare D1 default (DESIGN.md §3.3.1). Two layers guard every table: explicit GRANTs (ADR 0003) and Row Level Security. A person reads and writes their own characters; the Keeper can read the characters active in their campaign, plus a copy kept from each player who left, and can never write one (ADR 0001, 0011).
- **Accounts are Supabase Auth** (ADR 0007): email and password, or a magic link, both with the PKCE flow. Only an approved email can make an account (next point). Supabase stores each password as a salted bcrypt hash; the app only sends it to Supabase over TLS and must never store, hash, log or echo one. Minimum 12 characters, maximum 72 bytes, no composition rules (`validatePassword` in `js/util.js`; the server enforces the same minimum). Emailed links must be opened in the browser that asked for them. Errors shown to people go through `friendlyError` and never say whether an email exists. `?next=` return paths go through `safeNextPath` (same-site paths only). A trigger on `auth.users` creates the profile row (migration 0007). Don't hand-roll sessions.
- **Who can make an account:** only an email in `approved_emails` whose approval has not ended (7 days, ADR 0014). Supabase Auth's "before user created" hook, the Postgres function `hook_require_approved_email`, refuses every other new account, for a password sign-up and a magic link alike; `supabase/config.toml` sets it (`tests/unit/config.test.js` checks it), and `enable_signup` stays `true`. Only the owner (the dashboard or the service role key) can make an account that skips it. It runs as `supabase_auth_admin`, which may read only `approved_emails.email` and `expires_at`. The page shows a refused sign-up or link the same text as any other (`isUnapprovedEmail` in `js/util.js`); only the HTTP status and Auth's rate-limit answers can tell those emails apart. A **site admin** (`site_admins`, no client access at all) approves emails on the Admin page through `approve_email`, `revoke_approval`, `list_accounts` and `list_pending_approvals`; each refuses anyone else, and `is_site_admin` shows the Admin link (a failed check counts as "not an admin"). Only a confirmed account uses an approval: until the email is confirmed the account may be someone else's, so the approval still waits, can be revoked, and the account shows "Not confirmed". At most 20 approvals that have not ended wait for an account; an approval is kept after its account is made. The owner manages the admins with `npm run admins add|remove|list <email>`, and `npm run admins approve <email>` approves an email when no admin can (the owner's own, before any account exists). A site admin is not a Keeper and not a campaign creator.
- **Who can create a campaign:** only people on the `campaign_creators` allowlist (ADR 0005). Nobody can add themselves; the owner manages it with `npm run creators add|remove|list <email>` (plain words, no `--`, which PowerShell drops) (the person must have an account). Campaign creation is closed by default.
- **How players join:** only through an invite the Keeper creates on the Keeper page. A link opens a confirmation (`preview_invite`), and nothing joins until the player presses the button (ADR 0012). `campaign_players.invite_id` records the invite used. `replace_invite` ends an active invite and makes a new one like it. A campaign has at most 50 active invites and 500 in all. Invites are server-generated (120 bits), stored only as a SHA-256 hash, expiring, use-limited, revocable, and shown to the Keeper once. The client never generates or stores a code, and the API never returns one (`create_invite` / `revoke_invite` / `join_campaign`, ADR 0005).
- **Nothing is ever deleted by a client.** The DELETE grants and policies on campaigns and characters are gone, and a trigger snapshots every delete, every `schema_version` change and (at most every 10 minutes) every edit into `character_history` (ADR 0004).
- **Characters belong to people** (ADR 0011). `characters` has no campaign. `campaign_characters` says which character a player has active in a campaign: one per player per campaign, and a character in one campaign at a time. Only `choose_character`, `leave_campaign` and `remove_player` write it. A trigger allows 5 characters that are not deleted and 30 in all, per person (ADR 0014); at 5 the characters page turns off the buttons that make one and says to save a copy of one to the computer, then delete it (`FULL_NOTE` in `js/character-list.js`). "Delete" is `delete_character`: it sets `deleted_at` (a client cannot write that column) and refuses a character that is active; `undelete_character` brings it back. When a player leaves or is removed, `freeze_sheet` keeps a copy in `departed_sheets`, and the Keeper reads that copy, never the live sheet. The Keeper reads a character's history only from `assigned_at`.
- **The rulebook** (ADR 0016): the player's book only, shown as its authors wrote it. `rulebook` (one row: title, version) and `rulebook_pages` (place, slug, title, Markdown of at most 256 KiB) have RLS on, one `select` policy for `authenticated`, and a `select` grant to `authenticated` only: `anon` reads nothing and no client writes. The owner replaces the whole book in one transaction with `npm run rulebook push <folder> [staging]` (`scripts/rulebook.mjs`): a folder outside the repo with `book.json` and one `05_combat_basics.md` file per chapter (place 5, `/rules/combat-basics`, title from the first `# ` heading), sent base64-encoded in a SQL file (`runSqlFile`), printing only counts and titles. `/rules` is the contents, `/rules/<slug>` a chapter with the chapters either side (`rulebook.js` reads, `rulebook-view.js` draws). **No text of the real book is ever in this repo** (code, tests, fixtures, docs), because the repo is public: tests use made-up chapters.
- **The Markdown reader** (`js/markdown.js`): `parseMarkdown` is pure and makes a tree of its own tags and attributes; `renderMarkdown` builds it with `h()`. It reads headings (id `sec-` plus the GitHub slug), paragraphs, bold, italics, nested lists, GitHub tables (in a `.table-scroll` box the keyboard can reach), block quotes, rules, inline code, code blocks and links to `#part`, `/rules/<slug>` and `https:` (with `rel="noopener noreferrer"`). Raw HTML stays text, an image shows its alt text, any other link shows its text only. `tests/unit/markdown.test.js` checks each, and that no other tag or attribute can appear.
- Eclipse hosts about 10 people and at most 4 campaigns (ADR 0014), and the sheet and rules will change over time (ADR 0004).

## Working in this repo now
- **The game master is the Keeper.** Use "Keeper" in every text a person sees and in the docs, never "DM" or "GM". Code and database names that already say `dm` (`dm_sees_character`, `roster-view.js`) keep it: a rename there costs a migration and helps nobody.
- **Only `public/` is published.** `wrangler.jsonc` sets `assets.directory` to `./public`; everything in that folder is served publicly, and nothing outside it is. Site files (HTML/CSS/JS/images/fonts, plus `_headers` / `_redirects`) go in `public/`. Repo tooling and docs (`wrangler.jsonc`, `package.json`, `CLAUDE.md`, `.github/`, `supabase/`, `docs/`, `scripts/`) stay at the repo root. Wrangler does not skip `.git` or `node_modules` when uploading, so pointing `assets.directory` back at the repo root would publish them (and fail the deploy on large binaries).
- **Verifying what is published.** `npx wrangler deploy --dry-run` must exit 0 and report `Read N files`, where N counts every file **and subdirectory** under `public/` (`find public -mindepth 1 | wc -l`, currently 63). Because of the SPA fallback, a request for a path that does not exist answers `200` with the app shell, not `404`. So the check for `/DESIGN.md`, `/wrangler.jsonc`, `/package.json`, `/.git/config` and the like is that the response is the app shell (`<title>Eclipse</title>`) and never the file's contents. Do not run a real deploy to verify.
- Layout of `public/`: `index.html` (shell), `style.css` (site), `sheet.css` (the sheet only, all scoped to `.sheet`), `script.js` (theme switcher only), `logo.svg`, `_headers` (security headers and CSP), `js/` (the app's ES modules), `vendor/` and `fonts/` (third-party files, never edited).
- **Page layout follows deyderae.dev.** The header (sticky from 40rem up) and the footer band are the apex site's. The header bar is the full width of the window, like henrichsen.dev: the brand is at the left edge, and the account buttons and theme switcher are at the right edge. It has the same gutter on both sites, so the logo does not move between them. The footer icons use `--icon`, Catppuccin green (mixed toward `--text` in Latte for contrast). The wordmark is "Eclipse" and "Survivor's Records" (that part hides on a phone). `Admin` (shown only to a site admin), `Characters`, `Rules` and the account name in the header are `btn btn-quiet btn-small` buttons, like Sign out; on a phone they are one row when they fit, and a button that does not fit goes to the next row. `.page` is 72rem wide, like the footer text, and its content is a 50rem column, centred, unless `show()` is given `roomy` (a grid of cards) or `wide` (the sheet). Hover follows the apex site, except that a card holding buttons gets a stronger border and a shadow with no lift, so it does not look like one big link (`--hover-title`, 0.2s fades, and the reduced-motion rule at the end of `style.css`). The sticky Reference bar in `sheet.css` sits at `--header-h`, which `app.js` measures. Header and footer CSS are still copied from the apex site (DESIGN.md §3.4).
- **The sheet's code** (ADR 0008). `js/eclipse-content.js` holds the game's content: every table, name and rule number, written once (no logic, no DOM, no Supabase). Each table says `Stored` (a saved sheet keeps its names or keys) or `Not stored`. `js/eclipse-rules.js` holds the state shape and every rule as pure functions that read those numbers (no DOM, no Supabase; the Keeper roster imports it too). The sheet's pages, `render.js` and the Reference cards read the same values: a Reference table that repeats a rule is data in `sheet/reference-data.js` that the tab builds with `h()` (its prose stays `staticHtml()`), and `tests/unit/content.test.js` checks each such table against the rules. `js/characters.js` reads and writes a person's characters, their active characters and their history (`history-view.js` is the history page, `history.js` its wording; `character-views.js` is the characters page and the chooser, `character-list.js` its pure part), `js/autosave.js` is the debounce and retry state machine. `js/roster.js` (pure) builds the Keeper's roster and backup file from rows, `js/roster-view.js` draws it, and `js/data.js` has the Keeper's reads and the Realtime subscription. `js/sheet/` is the view: `*-page.js` build each page with `h()`, `render.js` draws numbers from the inputs, `bindings.js` turns input into changes to the sheet, `rebuild.js` redraws rows that come and go, `files.js` reads and writes `.eclipse` files, `index.js` is the view (tabs, save bar, conflicts).
- **Sheet rules that must hold.** Store inputs only, never a computed number. A sheet is only shown after it loaded and `openSheet` read it; never write before that. Unknown fields are kept (`normalize`). A stored `schema_version` newer than `SCHEMA_VERSION` opens read-only. A rename, removal or retype of a stored field is a new `SCHEMA_VERSION` plus a step in `MIGRATIONS`, never silent. Saves are conditional on `updated_at`; a mismatch is a conflict the player resolves, never an overwrite. A stored name that picks a row from a rules table goes through `own()` (so "constructor" matches nothing). The checklist for a rules change is ADR 0013: adding a field or a table row needs nothing extra; a rename, removal or retype needs the version bump and a tested migration step; a named table row (a race, a profession, a skill, a spell school) is retired, not deleted, once a sheet can point at it.
- **Restoring goes through `restore_character_version()`** (migration 0008), never a plain update: it is always snapshotted (reason `restore`), it needs the `updated_at` the page last saw, it needs ownership, and it refuses a deleted character. The snapshot trigger reads the `eclipse.restoring` setting the function sets for one transaction.
- **The Keeper's pages never write a sheet.** No insert, update, delete or RPC from the Keeper's sheet views, and the roster only reads. Its two actions (`remove_player`, and filling in the invite form) are callbacks the Keeper page gives it (ADR 0012) (`sheet/index.js` is read only when it is given a `readOnlyNotice`). A Keeper page opens a character only while it is active in that campaign. Realtime only tells the page to look; `syncRoster` re-reads changed rows by `updated_at` (and each departed copy once), and a 30 second check backs it up. `tests/e2e/fake-supabase.js` fakes the Realtime websocket (`window.__realtime.emit()` and `.drop()`).
- **Fonts are self-hosted**: `npm run vendor` copies the pinned `@fontsource` Latin woff2 files and their OFL licenses into `public/fonts/`; `font-src 'self'` is in `_headers`. Asset URLs are root-absolute (`/style.css`, `/js/app.js`) because deep links like `/characters/x` would break relative ones.
- **The Supabase client is vendored.** `public/vendor/supabase.js` is a byte-for-byte copy of the pinned `@supabase/supabase-js` browser bundle (the CSP allows scripts from `'self'` only, and there is no build step). Never edit it. To upgrade: change the version in `package.json`, `npm install`, `npm run vendor`, commit the result.
- `public/js/config.js` holds the project URL and anon key. Both are public by design (RLS and grants protect the data). Never put the service_role/secret key or the database password anywhere under `public/`.
- **Rendering rule:** build DOM with `js/dom.js` (`h()`, and `s()` for SVG), which only ever adds text as text nodes. Never use `innerHTML`, `insertAdjacentHTML` or `document.write` with anything that came from the database or the user: campaign, player and character names are user-controlled. The one exception is `staticHtml()`, for markup that lives in this repo (the Reference cards); `tests/unit/sources.test.js` fails on any other use. Attach handlers with `addEventListener` (the `on*` props of `h()` do this), never as inline attributes. No `style` attributes either: use a class, or set a CSS custom property from script (`el.style.setProperty("--pos", ...)`, which the CSP allows).
- Keep `js/util.js`, and the matcher and the leave gate in `js/router.js`, free of DOM and Supabase imports so they stay unit-testable in Node.
- Accessibility of navigation: after an in-app navigation focus moves to the new `<h1>`; on the first render it does not (moving it there would make Tab skip the skip link and the header).
- **Leaving a view.** A view that may hold unsaved changes gives `show()` a `flush`. Before every change of view (a link, `router.go()`, Back and Forward, `router.refresh()` when the sign-in changes, and Sign out) the router asks `mayLeave()`, which calls `flush` and asks the person only when it resolves false. One check runs at a time. Once the view is left, `main` is `inert` until the next `show()`, so nothing can be typed into a page that is on its way out. Change the view only through the router, never by calling `onRoute` directly.
- The theme system (Catppuccin, 4 palettes, `data-theme` attribute + `localStorage`) is duplicated from `deyderae-site`. Per DESIGN.md §3.4 that duplication is a known issue to fix, not a pattern to copy again — check whether a shared source has been extracted before touching it. In `public/style.css`, everything above the `Site layout` comment (palettes, reset, `color-scheme`) is the shared block and must stay byte-identical to the first 62 lines of `deyderae-site`'s `public/style.css`; don't change it here without changing the apex too. Eclipse-only CSS goes below that comment, and the theme logic in `public/script.js` stays separate from any site-specific code. `public/logo.svg` is a shared asset copied from the apex, so the same rule applies to it.
- No inline `<script>`, `<style>`, `style=` attributes, `on*` handlers, or `data:` URIs (DESIGN.md §4, §5.1) — they block the strict CSP in `public/_headers`. That policy allows scripts, styles and images from `'self'` only, and `connect-src` only for the live Supabase origin (`https://` and `wss://`). Nothing in `public/` names the staging project (`tests/unit/projects.test.js` checks); only the dev copy's `_headers` names staging instead. Any new origin (a font host, another API) must be added there deliberately; never use `unsafe-inline` or `unsafe-eval`. Self-host fonts (woff2 in `public/fonts/`, `font-src 'self'`); don't load Google Fonts.
- New colours must meet WCAG AA in all four themes, Latte especially (DESIGN.md §4). The sheet has two kinds of accent token in `sheet.css` (plain for fills and borders at 3:1, `-t` for text at 4.5:1), and `tests/unit/contrast.test.js` checks both in every theme, so add a colour there and run `npm test`: use `--text`/`--subtext1` for small text, never `--subtext0` or `--overlay*`, and for coloured links or badges mix the accent toward `--text` (`--link` is `color-mix(in srgb, var(--blue) 75%, var(--text))`). Form and button borders need 3:1 against their background (`--field-border` is 70% `--text` into `--base`; 62% failed on Latte). Large text (24px, or 18.66px bold) only needs 3:1. Don't dim disabled things with `opacity`; use a dashed border. Never write `*/` inside a CSS comment — it closes the comment early and silently swallows the next rule.
- `package.json` pins dev tooling and nothing runs from `node_modules` in production: Wrangler (`npm run dev` for local preview on port 8787 against the staging project (below), `npm run deploy` only as a fallback: Cloudflare Workers Builds deploys every merge into `main`, so a migration is pushed before its pull request is merged (README, Releasing a change)), the Supabase CLI (also behind `npm run creators`, `npm run admins` and `npm run rulebook`, which share `scripts/account-lists.mjs`, and `npm run staging`; `scripts/supabase-target.mjs` points each at live or staging), and `@supabase/supabase-js` (only as the source for `npm run vendor`). All are pinned exactly where DESIGN.md §5.4 asks. `npm run backup` saves the live data to a secret file outside the repo with the installed `pg_dump` (it asks for the database password), `npm run backup:check <file>` loads one into a throwaway database, and `npm run rehearse <file>` runs the current `openSheet` over every sheet in one, to catch a bad migration before it ships (README, Backups). `npx supabase ...` resolves the local CLI; don't install it globally.
- **Database changes** are new numbered files in `supabase/migrations/`, never edits to an applied one, applied with `npx supabase db push` (run `--dry-run` first). A new table needs its RLS policy **and** its GRANTs in the same migration (ADR 0003), and `supabase/tests/grants.test.sql` extended. Grants are **per column** for INSERT and UPDATE (ADR 0006): a column the server controls (ids, timestamps, foreign keys) must never be client-writable, so a new writable column needs an explicit grant and an assertion. The test harness (`supabase/tests/local_auth_harness.sql`) must mirror the real platform's default privileges and never be more permissive; its `supabase_auth_admin` (the role Auth runs hooks as) has nothing in `public` that a migration does not grant. Run `npm run test:db` (harness, every migration, every `*.test.sql` suite, in a throwaway database; needs a Postgres, use 17 to match the live project) for any change that touches the schema. Every suite raises on failure, so it gates CI. A code from `create_invite` is unrecoverable by design: if a link is lost, revoke that invite and create a new one.
- **Supabase project settings** are mirrored in two deliberately minimal files: `supabase/config.toml` (live) and `supabase/staging.config.toml` (staging). `npx supabase config push` writes everything declared in `config.toml` to the LIVE project, and the CLI fills undeclared sections with its own defaults, so never regenerate either file from `supabase init`, and always run `npx supabase config diff` before a push (`npm run staging check` for staging). Both set the sign-up hook, so push the migration that makes the function first; `tests/unit/config.test.js` checks that the two keep the same hook, password rules and email rules, that live redirects only to the live site, and that staging has no custom SMTP.
- **Development uses the staging project** (ADR 0015), never live. `npm run dev` (`scripts/dev.mjs`) serves a copy of `public/` in `.wrangler/dev-public` whose `_headers` and `js/config.js` name staging (`devRewrites` in `scripts/projects.mjs`), and copies each edit to `public/` into it; if either file no longer names the live project as expected, it stops. The browser tests still serve `public/` itself. Staging's URL and anon key are in `supabase/staging.json`. `scripts/supabase-target.mjs` picks the project for `npm run staging push|check`, `npm run admins … staging`, `npm run creators … staging` and `npm run rulebook push <folder> staging`: live runs in the repo, on its link; staging runs in a new folder outside the repo (staging config, a copy of the migrations, no link) with `--project-ref` on every command, so it can never fall back to live. Never link the repo to staging. A new migration goes to both: `npx supabase db push` and `npm run staging push`.
- Tests: `npm test` runs the unit tests (Vitest, `tests/unit/`, including the rules, autosave, contrast and source checks); `npm run test:db` runs the database suites. `npm run test:e2e` runs an automated accessibility scan of every page in two themes (axe, `tests/e2e/a11y.spec.js`) with the rest of the browser suite (Playwright, `tests/e2e/`) against the real `wrangler dev` server, so the real CSP applies; it uses Edge (`E2E_CHANNEL=chromium` elsewhere) on port 8798 (`E2E_PORT` changes it, so two runs can share a machine). `tests/e2e/fake-supabase.js` stands in for Supabase inside the page (including a `characters` table that enforces the column grants, the `updated_at` match and the 5-character limit, the sign-up hook, the admin functions that refuse a non-admin, and a made-up rulebook, `RULEBOOK` in `tests/e2e/helpers.js`, that a signed-out request cannot read), and every test fails on a CSP violation or an uncaught error. It cannot prove that email arrives. CI (`.github/workflows/ci.yml`) runs on every push and pull request, one job per area: `unit`, `database` (Postgres 17), `browser` (Chromium), `publish` (the dry run and its file count), `vendor` (`npm run vendor` must change nothing) and `audit` (`npm audit --audit-level=high`). Dependabot (`.github/dependabot.yml`) opens grouped updates each week; the `vendored` group fails `vendor` until someone runs `npm run vendor` on its branch and commits the result.
- Once this app handles user data, treat DESIGN.md §5.5 (input validation, rate limiting, least-privilege bindings) as required reading before writing any backend logic, not optional hardening to add later. Every new table is a security decision.

## Don't
- Don't lose a character. Eclipse hosts about 10 people in at most 4 campaigns, and the sheet and rules will keep changing (docs/adr/0004-scale-and-data-preservation.md): never build UI that deletes a campaign or removes a character (hiding one with `delete_character` is the only "delete"), never write a sheet before it has loaded successfully, keep unknown fields on save, and make non-additive sheet changes versioned (`characters.schema_version` plus a `migrate()` step), not silent.
- Don't point `assets.directory` in `wrangler.jsonc` back at the repo root, and don't put non-site files (docs, config, source that isn't served, secrets) in `public/`.
- Don't commit secrets, tokens, or (once there's a database) real user data/fixtures.
- Don't put the Supabase service role key in client code, the repo, or logs — it bypasses RLS entirely. The `anon` key is public by design; RLS is what makes that safe (DESIGN.md §5.3).
- Don't wire this Worker directly to a shared database credential used by other subdomains — route through a dedicated API service if cross-subdomain data sharing is ever needed (DESIGN.md §3.3). Eclipse's Supabase project is its own boundary: nothing else on the domain should hold its service role key or read its tables directly (DESIGN.md §5.6).
